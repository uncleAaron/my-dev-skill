# 验证与测试案例沉淀

先读取 acceptance.json、verifications.json 与 AC。测试命令必须真实运行；unit/integration/contract/e2e 必须报告实际执行数，当前支持 unittest 输出与 JUnit XML。零用例、跳过、未知、失败和超时均不能自动满足测试 AC。预期报告目录先由项目 .gitignore 明确排除；生成文件若改变工作区指纹，分析后重新执行。

测试层级选择：纯规则用单元测试；Spring Boot MVC/持久化用项目已有切片或数据库集成测试；外部 HTTP 用契约或项目已有 Mock；真实跨服务使用隔离环境。Mock 只证明约定范围，不能证明真实下游已联通。环境缺失保留阻塞，完成无依赖任务。

每次数据准备使用运行 ID、独立业务键或测试命名空间。记录依赖、创建、清理命令和所有权，只清理本次数据；不能依赖共享环境里碰巧存在的数据。公司内网缺少依赖时列明需要的离线包/内部地址，不自动访问外网。

执行前预扣 task attempt，调用 run 并读取 validation_errors。测试断言必须验证业务状态和副作用，不只看 HTTP 200。修复缺陷先得到失败复现，再改代码，再回归；禁止减少原断言或把用例 skip 来收口。

verification.md 写 AC→测试文件→run_id、执行时间、指纹、测试数、下游模式、语义审查与未验证项。test-cases.md 保留可重跑入口、输入、期望、数据准备、隔离与清理。运行证据在 .workflow，移机前按授权脱敏归档；无原始证据时重跑。

整体验收前重跑因后续修改而失效的相关验证。复验已有 passed 任务时，重新开启 --repair 尝试，预算照常计算；验证不是对抗恶意写文件的安全机制。
