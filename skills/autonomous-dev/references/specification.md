# 特性文档

读取当前需求、项目规则、相关代码和命中的历史经验。填写 feature.md，保留原始需求来源与修订原因。

逐项写出：业务目标、角色、范围、非目标、规则、正常/异常/边界场景、权限和非功能要求。用 `| AC-01 | 要求 | 可观察条件 |` 表格定义稳定验收编号。描述输入、触发、期望结果；接口返回成功不能替代业务正确。

对每个歧义判断是否影响业务结果、兼容、数据归属或不可逆操作。关键问题记录并询问，其他可逆取舍记录依据后继续。用户提出范围变化时执行 revise，重新分析影响。

将 AC 同步到 acceptance.json，每项为 `id`、`verification_ids`、`downstream`。真实下游要求写 real；允许 Mock 的条件写 mock，无下游写 none。可在计划阶段补全 verification_ids，plan 门禁前必须完整。以真实业务需求决定验证模式，不为绕过环境缺口降低要求。

完成条件：每项规则可观察、异常和边界已覆盖、范围清晰、关键问题已解决或显式阻塞。审查后自动进入设计。
